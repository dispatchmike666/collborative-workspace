# Stages 2 to 5: Hub, Helpers, Shared Projects - Plan

**Goal:** Brennan and Max log in to one website, see the same projects, and each talk to their own Claude (running on their own computer, on their own Claude plan) while both watch live. Claudes share project files through GitHub, take turns quietly, and the window also has team chat, shared notes, an approve button, and a preview.

**Spec:** `docs/superpowers/specs/2026-10-14-shared-workspace-design.md` (stages 2 to 5 of section 9). Stage 1 results: `docs/superpowers/stage-1-results.md`.

**Written 2026-10-23, built the same day by the same session, so this plan lists tasks, interfaces and checks. It does not repeat all the code.**

## Terms check (spec section 8, before Stage 2)

Re-read on 2026-10-23 from search results quoting Anthropic's Claude Code legal page. I could not read the official page text directly. What it says, in short:
- Using Claude Code on your own plan for your own work is the intended use, including `claude -p` in your own scripts.
- Anthropic does not allow third-party tools that offer Claude plan logins to other people or route requests through plan credentials on behalf of users. Sharing one account between two people is against policy.
- This design stays on the allowed side: each person's helper runs their own Claude on their own computer with their own login, and only handles that person's own requests. A person's request is never sent to someone else's Claude.
- This is not legal advice. Brennan decides whether to rely on it.

## Global constraints (added to Stage 1's)

- Zero npm packages. Node built-ins only (`http`, `crypto`, `fs`, `child_process`, `fetch`, `node:test`).
- No API key anywhere (guard test stays green). Passwords and helper tokens are generated by the hub's command-line tool and written to a local file the person reads. They are never typed or pasted by the assistant.
- Only two people can log in: users created with `hub/cli.js`.
- A message for the AI goes only to the sender's own helper.
- All messages to Claude go through stdin. All git and Claude commands use argument lists, never a shell.
- The hub listens on 127.0.0.1 only. Exposing it to the internet is done by the person with a tunnel or a host, and the hub then needs `HUB_PUBLIC_HOST` set.
- Everything a person reads is plain English.

## Decisions made while planning

- **Projects are a name plus an optional GitHub repo URL** (https://github.com/owner/repo). Sharing files between two computers needs a repo. Each helper clones it into its own folder using the git login already saved on that computer. The hub never handles git credentials or tokens, so nothing secret passes through it.
- **Hosting is left to the person.** The hub is a plain Node program. Brennan runs it on his PC and exposes it with a tunnel, or puts it on any host that runs Node. Instructions go in `docs/hosting.md`. (Creating accounts and installing tunnel software is something only Brennan can do.)
- **Data lives in plain files** under `hub-data/` (JSON and JSON-lines), written safely. No database to install.
- **Live updates use Server-Sent Events** (the page and the helpers keep a connection open and the hub pushes). Helpers connect out to the hub, so nobody's computer opens a port.
- **Turn-taking is decided by the hub.** One active run per project. Queued runs whose owner's computer is offline wait without blocking the other person.
- **Approvals:** when a run ends with blocked commands, the hub shows each exact command with an "Allow once" button for the owner of that Claude only. Approving starts a new run on the same conversation with a one-command allowance. Checked by hand: this works.
- **Preview:** after a run, if the project has an `index.html` at its top level, the helper uploads the site's small files. The hub serves them in a sandboxed frame (`Content-Security-Policy: sandbox`) so the previewed site cannot touch the hub or its login.
- **Trust:** whoever runs the hub can send prompts to both Claudes. Max trusts Brennan's hub. Claude on each computer only edits inside the project folder, and commands needing approval stay blocked.

## Contracts

### Events on a project's timeline (stored)

`user {who, text}` · `team-chat {who, to, text}` · `status {state: queued|waiting|working|idle, who, ...}` · `run-start` · `claude-text` · `claude-step {tool, summary}` · `claude-step-result {ok, text}` · `run-done {ok, text, durationMs, costUsd}` · `error {text}` · `sync {text}` · `approval-needed {approvalId, owner, tool, command, description}` · `approval-used {approvalId, by}` · `notes-saved {who, version}`.
Events produced by a helper carry `owner` (the user whose Claude produced them). Every stored event gets `id` and `at`.

### Hub to browser (SSE at `/api/projects/:id/stream`)

Stored events (replayed after `Last-Event-ID`), plus unstored: `presence {online: {name: bool}}`, `files {files: [path], changed: [path]}`, `preview {version}`.

### Helper to hub

- `GET /helper/connect` (SSE, `Authorization: Bearer <token>`): hub sends `job {jobId, projectId, projectName, repoUrl, who, text, recap, allowedTools}` and `ping`. An open connection means "online".
- `POST /helper/events {jobId, events: [...]}`: events are appended to the project's timeline stamped with the owner.
- `POST /helper/done {jobId, ok}`: releases the project lock.
- `POST /helper/files {projectId, files, changed}`, `POST /helper/preview {projectId, files: [{path, data}]}` (data is base64).

## Pass/fail checks (from spec section 9)

**Stage 2:** a second user logs in and their own helper runs their own Claude; each person sees both timelines live; a message from one person never reaches the other's helper (tested on purpose); an unknown name or wrong password cannot log in.
**Stage 3:** a change one Claude saves is present for the other's next run; a second request while one runs shows "waiting in line", starts alone, and the sender can keep chatting; the recap lets a Claude answer "what did the other person just change?".
**Stage 4:** create and open projects from the home page; "Just <name>" messages never reach any AI; shared notes edit with a conflict warning.
**Stage 5:** after a run that makes an `index.html`, the preview shows in the window; if there is no `index.html`, the preview area says why.

## Known limits (written down now, not discovered later)

- Two people typing in the same note at the same second: the second save is refused with a plain message and nothing is overwritten.
- If the hub restarts during a run, that run is marked failed and the next one starts.
- Helpers on two computers need the same project repo reachable with each computer's saved git login. Max must be added to the repo on GitHub by its owner.
- Plan allowance per message is real; the window shows it.
